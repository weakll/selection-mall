# 交易一致性

## 库存原子扣减

下单前由订单服务调用商品服务内部接口：

```text
POST /internal/product/deductStock
```

商品服务在本地事务中逐项执行条件更新：

```sql
UPDATE product_sku
SET stock_num = stock_num - #{num}
WHERE id = #{skuId}
  AND stock_num >= #{num}
  AND is_deleted = 0;
```

任意 SKU 更新行数不为 1 时抛出库存不足异常，商品服务事务整体回滚。该方式避免先查询、再扣减产生的并发超卖窗口。

## 订单落库补偿

库存扣减成功后，如果订单、订单明细或日志落库失败，订单服务会调用：

```text
POST /internal/product/restoreStock
```

恢复本次已预占的库存。恢复失败会记录错误日志，为后续库存对账任务保留排查依据。

## 订单提交幂等

H5 在进入确认订单页时生成一次 `requestId`，同一页面内的重试复用该值。订单服务使用 Redis 原子写入：

```text
mall:order:submit:{userId}:{requestId}
```

- 首次请求写入 `PENDING`，锁有效期为 2 分钟。
- 订单事务提交成功后，缓存 24 小时内的订单 ID。
- 重复请求直接返回已创建订单 ID，不重复扣减库存。
- 库存扣减或订单落库失败时释放锁并恢复库存。

## 支付回调幂等

支付记录使用条件更新：

```sql
UPDATE payment_info
SET payment_status = 1
WHERE order_no = ? AND payment_status = 0;
```

并发重复回调只有一个请求能把支付记录从未支付更新为已支付，失败请求重新读取状态，已支付则直接返回。

订单状态同样使用 `order_status = 0` 条件更新，只有首次支付回调会记录支付成功日志。

## 支付成功

库存已经在下单阶段预占，因此支付回调成功时只增加商品销量，不再重复扣减库存。

## 缓存一致性

库存扣减、库存恢复、销量更新和支付后的商品变更都会清理商品详情缓存，避免继续读取旧的库存或销量。

## 内部接口边界

库存和销量接口统一放在 `/internal/product/**`。网关只转发 `/api/product/**`，不对公网暴露内部接口。

## 当前边界

- 库存预占和订单落库之间使用补偿，不是分布式强事务。
- 定时任务扫描超时未支付订单，使用状态条件更新关闭订单并回补库存；只有首次关闭成功的任务实例执行回补。
- 库存回补失败会记录订单号和商品明细，持久化对账和自动重试任务仍属于后续生产增强项。

这些边界会在后续交易一致性改造中继续处理。
