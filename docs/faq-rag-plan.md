# 客服知识库 RAG 检索 + 效果评测 —— 实施方案

> 目标：把 `service-ai` 的售后政策检索从"7 条关键词命中"升级为**可量化评测的混合检索链路**，
> 并在简历上形成一条有数据的成果："构建 N 条标注问答集，对比四种检索配置，
> Top-3 命中率从 X% 提升至 Y%"。

## 1. 现状与约束（已实测）

### 1.1 现状

| 项 | 现状 |
|---|---|
| 知识库 | `ai/faq-knowledge.yml`，**仅 7 条**政策，启动时载入内存 |
| 检索方式 | 关键词包含匹配（`FaqTools.matches`），最多返回 3 条 |
| 基础设施 | MySQL 8.0.30 / Redis / Nacos —— **零新增** |
| 对话模型 | DeepSeek（`deepseek-chat`）已接入可用 |

### 1.2 三条硬约束

**① 知识库 7 条无法做评测 —— 必须先扩库**

7 条政策做检索评测，任何方法都能拿到接近 100% 的命中率，
四组配置的差距会被淹没在噪声里，**指标失去区分度**。
评测要有意义，知识库需要扩到 **不少于 50 条**（建议 60 条）。

**② 没有 Embedding / Rerank 的可用密钥**

已核查：本机只有 `DEEPSEEK_API_KEY`。
DeepSeek 官方 API **只提供对话模型，不提供 embedding 与 rerank**。
`DASHSCOPE_API_KEY` / `BAILIAN_API_KEY` / `SILICONFLOW_API_KEY` 等均未配置，
Ollama 也尚未运行。

**这决定了本方案必须分两期做** —— 见第 2 节。

**③ MySQL 中文全文检索可用，但有上限**

- MySQL 8.0.30，`ngram_token_size = 2`，支持 `FULLTEXT ... WITH PARSER ngram`
- 局限：**对同义改写不敏感**。用户问"东西不想要了怎么办"，
  政策原文写"退换货"，纯全文检索召回不到——这正是向量检索要解决的问题

## 2. 分期实施

### 第一期（可立即开工，零外部依赖）

| 能力 | 技术选择 | 依赖 |
|---|---|---|
| 关键词召回 | 现有词表匹配（基线） | 无 |
| 全文召回 | MySQL `FULLTEXT ... ngram` + BM25 打分 | MySQL（已有） |
| 融合 | RRF | 无 |
| 精排 | **DeepSeek 做 LLM 相关性打分** | DeepSeek key（已有） |
| 评测框架 | 标注集 + Recall@k / MRR | 无 |

第一期就能产出**四组配置的对比数字**，简历要的那条数据在这一期就能拿到。

关于用 LLM 做精排：这是业界真实存在的做法（LLM-as-Reranker），
不是权宜之计。代价是比专用 Rerank API 慢、贵，但**相关性判断质量通常更高**，
因为它是逐对判断而不是向量点积。简历上可如实写"基于 LLM 的相关性精排"。

### 第二期（需要额外密钥或本地模型，二选一）

| 选项 | 代价 | 得到什么 |
|---|---|---|
| **A. 申请百炼 API Key** | 免费额度即可，需实名 | 真正的 Embedding（`text-embedding-v3`）+ Rerank（`gte-rerank`），简历技术栈那句话落地 |
| **B. 本地 Ollama** | 下载约 2–4 GB 模型 | 零 API 成本、数据不出本机；`nomic-embed-text` 等；但本机需能跑动 |

第二期在第一期之后叠加：**向量召回 + RRF 三路融合 + 专用 Rerank**，
再跑一次评测，得到"加向量检索后提升了多少"的增量数据。

> 建议：**先做第一期拿数据，同时去申请百炼 Key**。
> 即使第二期最终没做成，第一期的评测成果已经足够写简历，
> 而且"为什么没上向量库"本身就是一个能答得很漂亮的面试问题。

## 3. 评测设计（本方案的核心）

大部分简历写"实现了 RAG 检索"却不给数据。评测是这条成果的价值所在。

### 3.0 实测结果（已完成）

知识库 63 条，标注集 120 条（书面 63 / 口语 42 / 多意图 10 / 越界 5），评测 topK=5：

| 配置 | Recall@1 | Recall@3 | Recall@5 | MRR | 越界拒绝率 |
|---|---|---|---|---|---|
| A 词表匹配（改造前） | 46.1% | 79.1% | 79.1% | 0.625 | 100.0% |
| B 全文索引 + BM25 | 88.7% | 94.8% | 95.7% | 0.918 | 60.0% |
| C RRF 融合 | 81.7% | 98.3% | 98.3% | 0.899 | 60.0% |
| D BM25 + LLM 精排 | 93.9% | 94.8% | 94.8% | 0.943 | 100.0% |
| **E RRF + LLM 精排（采用）** | **95.7%** | **96.5%** | **96.5%** | **0.961** | **100.0%** |

按问法类型 Recall@5：

| 类型 | 样本 | A | B | C | D | E |
|---|---|---|---|---|---|---|
| 书面 | 63 | 84.1% | 100.0% | 100.0% | 100.0% | 100.0% |
| 口语 | 42 | 66.7% | 88.1% | **95.2%** | 85.7% | 90.5% |
| 多意图 | 10 | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% |
| 越界 | 5 | 100.0% | 60.0% | 60.0% | 100.0% | 100.0% |

**选型结论：采用 E。** 单看 C 与 D 会发现一个矛盾——C 靠两路互补拿到最高召回，
但 RRF 只融合排名、把首位顺序拉平了；D 的排序与越界判断最好，却只用了单路候选。
串起来（E）同时拿到两者长处：Recall@5 只比 C 低 1.8pt，
换来 Recall@1 高出 14pt、越界拒绝率从 60% 提到 100%。
对客服场景而言"第一个答案对不对"与"不知道就别编"权重更高。

**三个值得记录的实测发现**（都是先量出来再改的，不是照惯例做）：

1. **中文不能切 1-gram。** 1-gram 会让"你们公司地址在哪里"这类越界问题拿到 22.41 分
   （高于部分有效查询）。只保留 2-gram 后降到 11.18，判别力显著改善。
2. **越界拒绝率无法靠阈值恢复。** 越界查询最高覆盖率 25%、有效查询最低 8%，
   区间重叠，任何单一阈值都误杀。覆盖率 0.15 + 分数 3.0 是折中，
   剩余漏网必须由 LLM 精排（语义判断）解决——这是组 D 存在的理由。
3. **MySQL `MATCH AGAINST` 不是 BM25。** 它是 TF-IDF 变体且 `k1`/`b` 不可配，
   因此分工为：MySQL 的 ngram 全文索引承载索引与候选过滤，BM25 在应用侧精算。

### 3.1 标注集构造

知识库扩到 60 条后，为每条政策构造 **2 个问法**，共约 **120 个查询**：

| 问法类型 | 示例 | 占比 | 考察点 |
|---|---|---|---|
| 书面问法 | "退换货政策是什么" | 40% | 与原文措辞接近 |
| 口语问法 | "东西不想要了怎么办" | 40% | 同义改写的鲁棒性 |
| 多意图问法 | "能退货吗？发票怎么开？" | 20% | 多政策召回能力 |

每条查询标注**正确的政策 id 集合**（多意图可对应多条）。

**构造纪律**：标注必须在写检索代码**之前**完成，且不得回看检索结果调整 ——
否则就成了"按答案调参"，指标会虚高，面试一问就露馅。

### 3.2 指标定义

| 指标 | 定义 | 为什么看它 |
|---|---|---|
| **Recall@1** | 正确政策排在首位的比例 | 客服场景最关心"第一个答案对不对" |
| **Recall@3** | 正确政策落在前 3 的比例 | 返回 3 条给模型，覆盖到即可 |
| **MRR** | 正确政策排名倒数的均值 | 反映排序整体质量，不是只看命中 |
| **无答案拒绝率** | 知识库确实无对应政策时，是否正确返回"查不到" | **最容易被忽略但最重要**——客服宁可说不知道，也不能编 |

最后一项尤其值得强调：它对应 `FaqTools` 现在"查不到就让模型转人工"的设计，
是**防止幻觉**的关键指标，比命中率更能体现工程判断。

### 3.3 四组对照配置

| 组 | 配置 | 预期 |
|---|---|---|
| A | 词表匹配（现状基线） | 最低 |
| B | MySQL 全文 + BM25 | 中 |
| C | B + RRF 融合词表 | 中高 |
| D | C + LLM 精排 | 最高 |

每组跑全部 120 条查询，输出同一张指标表 —— 这就是简历上那行数据的来源。

## 4. 落地步骤

| 步骤 | 内容 | 可验证产出 |
|---|---|---|
| 0 | **本方案确认**（本文档） | 方案定稿 |
| 1 | 知识库扩到 60 条：从商城业务衍生（退换货、物流、发票、优惠券、会员、支付、售后、超时、地址、评价等） | `faq-knowledge.yml` 60 条 |
| 2 | 构造标注集：120 条查询 + 正确政策 id | `faq-eval-set.jsonl` |
| 3 | 基线跑分：现有词表匹配 | 组 A 指标 |
| 4 | 建表 + 全文索引；实现 BM25 召回 | 组 B 指标 |
| 5 | RRF 融合 | 组 C 指标 |
| 6 | LLM 精排（DeepSeek） | 组 D 指标 |
| 7 | 评测脚本固化 + 输出对比表 | 可重复运行的评测命令 |
| 8 | 接入 `FaqTools.search`，客服回答质量对比 | 前后对话截图 |
| 9 | 文档 + 简历条目改写 | `docs/ai-service.md` 增补章节 |

**关键纪律：步骤 2 必须在步骤 3 之前完成。** 先标答案再写检索，
否则"按结果调参"会让数据失真。

## 5. 已知取舍与风险

| 风险 | 应对 |
|---|---|
| 60 条知识库仍是小规模，指标不能宣称"生产级" | 简历如实写"60 条标注集"；这本身就是小规模客服的真实形态 |
| MySQL 全文对中文同义改写召回差 | 这正是第一期的主要发现——**把它作为"为什么要上向量检索"的论据**，而不是藏起来 |
| LLM 精排慢且耗 token | 评测离线跑，成本可控；线上只对 Top-5 做精排 |
| 百炼 Key 未必申请得下来 | 第一期成果已独立成立；第二期作为增量，不影响简历主线 |
| 标注集有主观性 | 每条政策的问题由政策原文反推，答案唯一且可核对 |

## 6. 做完之后简历怎么写（预览）

`精选商城` 的 AI 客服部分会增加一条：

> **• 知识库检索与评测**：将售后政策检索从词表匹配升级为「MySQL 全文检索 + RRF 融合 + LLM 精排」
> 三阶段链路，构建 60 条政策、120 条标注问法的评测集，
> 对比四种配置，Recall@3 从 XX% 提升至 XX%，无答案拒绝率 XX%

> 附注：这里的 XX 必须在真跑完之后填，**不许预估**。
> 面试官问"这个数怎么来的"，你要能当场打开评测脚本重跑一遍。
